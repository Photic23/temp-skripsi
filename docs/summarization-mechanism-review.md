# Summarization Mechanism Review

## Overview

This document reviews the summarization pipeline implemented in `app.py`, analyzing
the behavioral differences between the mT5 multilingual model and the Claude LLM backend.
It covers identified issues in the mT5 pipeline, their literature basis, and proposed
solutions. The analysis is grounded in evaluation results from `results/results-bryan.json`
(mT5) and `results/results-claude-bryan.json` / `results/results-claude-fathir.json`
(Claude).

---

## Pipeline Architecture

All models share the same Flask endpoint and summarization flow. The backend model is
swapped via environment variables (`USE_CLAUDE`, `USE_GEMINI`, `USE_T5_INDONESIAN`,
`USE_LEXRANK`; default is mT5).

```
POST /summarize/forum
  │
  ├── clean_text() on each post's content
  │     (HTML unescape → strip tags → remove URLs → NFKC normalize → whitespace normalize)
  │
  ├── single root post → summarize_post_thread(post)
  │     └── depth-first recursion (bottom-up)
  │           ├── leaf node  → recursive_summarize(post_text, parent_context)
  │           └── inner node → summarize children → combine → recursive_summarize(combined)
  │
  └── multiple root posts → summarize_post_thread(p) for each p
                          → join summaries → recursive_summarize(combined)
```

`recursive_summarize` splits text into token-sized chunks and processes them with a
rolling context prefix (`"Ringkasan sebelumnya: {summary}. "`), calling `generate_summary`
on each chunk. `generate_summary` dispatches to the active backend model.

## Issue 1: Domain Mismatch (Acceptable — Model Limitation)

**What happens:** mT5 (`csebuetnlp/mT5_multilingual_XLSum`) generates news-style text
about named individuals rather than synthesizing collective forum themes.

**Why:** The model was fine-tuned exclusively on BBC news article–summary pairs from
XL-Sum (Hasan et al., 2021), a dataset of ~1 million article–summary pairs across 44
languages. Its learned prior is: *given a text, write a news lead about the most salient
named entity*. Forum posts containing student names trigger exactly this behavior.

**Status:** Accepted as a fundamental model constraint. Addressed only by switching to
a domain-appropriate model (e.g., a model fine-tuned on discussion data) or an LLM with
instruction following. Issues 2–5 below are fixable without changing the base model.

**References:**
- Hasan et al. (2021). *XL-Sum: Large-Scale Multilingual Abstractive Summarization for
  44 Languages.* ACL-IJCNLP Findings. https://arxiv.org/abs/2106.13822
- Xue et al. (2021). *mT5: A Massively Multilingual Pre-trained Text-to-Text
  Transformer.* NAACL. https://aclanthology.org/2021.naacl-main.41.pdf

## Issue 2: 512-Token Window Forces Fragmentation

### Description

In `app.py`, the per-chunk token budget is model-dependent:

```python
max_tokens = 32000 if (USE_GEMINI or USE_CLAUDE) else (4096 if USE_LEXRANK else 512)
chunk_budget = max_tokens - (CONTEXT_RESERVE if previous_summary else 0)
# For mT5: chunk_budget = 512 - 160 = 352 tokens when rolling context is active
```

A typical forum with 20+ replies easily exceeds 352 tokens. `chunk_text` therefore splits
the combined forum text into many small fragments, each covering only 1–2 posts. The
model never sees the full discussion at once and cannot synthesize themes that span
multiple posts.

Claude receives `max_tokens = 32000`, so most forums fit in a single call — no
fragmentation occurs.

### Literature Basis

Liu et al. (2023) demonstrate the *"lost in the middle"* phenomenon: language model
performance peaks when relevant content is at the beginning or end of an input window
and degrades significantly for content in the middle. When mT5 chunks each contain 1–2
posts, later posts in the chunk are effectively invisible to the model.

Independently, empirical work on multi-document summarization (Garg & Nenkova, 2025)
finds that *"the hierarchical chunking method exhibits significant degradation in summary
recall... and often skips details such as entities and numerals."* This directly explains
why mT5 summaries miss the collective themes present across forum posts.

### Proposed Fix

For small-window models, bypass the hierarchical bottom-up tree and instead flatten all
posts into a single document, truncating greedily to the token limit. This gives the
model a coherent, multi-author slice of the real discussion:

```python
def flatten_posts_for_small_model(posts, max_tokens):
    """Depth-first flatten all posts into a single truncated text."""
    lines = []
    stack = list(posts)
    while stack:
        p = stack.pop(0)
        content = p.get("content", "").strip()
        author = p.get("author", "Unknown")
        if content:
            lines.append(f"[{author}]: {content}")
        stack = p.get("replies", []) + stack

    text = ""
    for line in lines:
        candidate = f"{text}\n{line}".strip() if text else line
        if count_tokens(candidate) <= max_tokens:
            text = candidate
        else:
            break
    return text
```

In `summarize_forum()`, dispatch by model type:

```python
if not (USE_CLAUDE or USE_GEMINI or USE_LEXRANK or USE_T5_INDONESIAN):
    # mT5: flat approach avoids hierarchical compounding
    flat = flatten_posts_for_small_model(posts, 512)
    summary = recursive_summarize(flat)
else:
    # large-context models: existing hierarchical approach
    if len(posts) == 1:
        summary = summarize_post_thread(posts[0])
    else:
        thread_summaries = [s for s in (summarize_post_thread(p) for p in posts) if s]
        combined = "\n\n".join(thread_summaries)
        summary = recursive_summarize(combined)
```

## Issue 3: `min_length=80` Forces Hallucination on Short Inputs

### Description

The mT5 generation call enforces a hard minimum output length:

```python
output_ids = mt5_model.generate(
    input_ids=input_ids,
    min_length=80,        # forces at least 80 tokens of output
    max_new_tokens=256,
    no_repeat_ngram_size=3,
    ...
)
```

`MIN_TOKENS_TO_SUMMARIZE = 50` is intended to skip very short posts, but mT5's
subword tokenizer tokenizes Indonesian aggressively (1 word → 2–4 tokens), so posts
containing only 15–20 meaningful words can exceed 50 tokens and pass the gate. The
model is then forced to generate 80 tokens from minimal content. With
`no_repeat_ngram_size=3` preventing repetition, it fills the gap with hallucinated
content: fake names, fake institutions, news-style filler.

### Literature Basis

Maynez et al. (2020) establish that close to two-thirds of mT5 generations contain at
least one factual inconsistency with the source, even under normal conditions. They
trace this to the model's tendency to generate domain-typical content when source signal
is weak — a bias that `min_length` amplifies by forcing the model to continue generating
past the point where faithful content is exhausted.

Ji et al. (2023) report that up to 30% of abstractive summaries contain fabricated
facts, and identify length-enforcement during decoding as a contributing factor to
extrinsic hallucination (content not present in the source).

Deng et al. (2022) show explicitly that beam search with hard length constraints pushes
generation toward hallucinated paths: when the model has no more faithful content to
generate, beam search selects the next most probable token regardless of source
fidelity.

### Proposed Fix

Replace the hardcoded `min_length=80` with a value proportional to input length,
ensuring the model is never required to generate more than it can faithfully extract:

```python
input_token_count = len(mt5_tokenizer.encode(input_text, add_special_tokens=False))
dynamic_min = max(20, min(80, input_token_count // 3))

output_ids = mt5_model.generate(
    input_ids=input_ids,
    min_length=dynamic_min,   # scales with input, not hardcoded
    max_new_tokens=256,
    no_repeat_ngram_size=3,
    ...
)
```

A 30-token post will produce `min_length=20` instead of 80, removing the pressure to
hallucinate filler while still discouraging degenerate one-word outputs.

### References

- Maynez et al. (2020). *On Faithfulness and Factuality in Abstractive Summarization.*
  ACL. https://arxiv.org/abs/2005.00661
- Ji et al. (2023). *Survey of Hallucination in Natural Language Generation.*
  ACM CSUR. https://arxiv.org/pdf/2202.03629
- Deng et al. (2022). *Improved Beam Search for Hallucination Mitigation in Abstractive
  Summarization.* https://arxiv.org/abs/2212.02712

## Issue 4: Hallucination Compounds Through the Bottom-Up Tree

### Description

`summarize_post_thread` recurses depth-first, summarizing leaf posts first and passing
those summaries up as context for parent nodes. Each level of the tree treats its
children's output as ground truth:

```
leaf post (15 words) → hallucinated 80-token summary
  ↓
parent node combines: [real post text] + [hallucinated child summary]
  → summarizes → hallucinated output (compounded)
    ↓
    root node combines: [real post text] + [compounded hallucinations]
      → final summary (heavily hallucinated)
```

This issue is structurally linked to Issue 3: hallucinations injected at leaf level
propagate upward because no filtering step exists between tree levels.

### Literature Basis

Shaham et al. (2025) demonstrate in the multi-document setting that *"the likelihood of
omitting essential information through summarization grows with the number of reasoning
steps, jeopardizing the integrity of reasoning chains."* Each tree level in the bottom-up
approach constitutes one such reasoning step.

Chang & Xu (2021) note in the context of hierarchical dialog summarization that
higher-level summaries grow increasingly abstract and detached from source content —
a compounding effect that is acceptable when lower-level summaries are faithful but
catastrophic when they contain hallucinations.

### Proposed Fix

The flat-then-truncate approach described in Issue 2 eliminates the tree entirely for
mT5, removing the compounding mechanism. No additional change is required beyond the
fix in §Issue 2.

### References

- Shaham et al. (2025). *How LLMs Hallucinate in Multi-Document Summarization.*
  ACL NAACL Findings. https://aclanthology.org/2025.findings-naacl.293.pdf
- Chang & Xu (2021). *Hierarchical Summarization for Longform Spoken Dialog.*
  https://ar5iv.labs.arxiv.org/html/2108.09597

## Issue 5: `WHITESPACE_HANDLER` Erases Structural Information

### Description

Before tokenization, `app.py` applies:

```python
WHITESPACE_HANDLER = lambda k: re.sub(r'\s+', ' ', re.sub(r'\n+', ' ', k.strip()))
```

This collapses all newlines — including the `\n\n` separators inserted between posts in
`summarize_post_thread` — into single spaces. The structured input:

```
[Author A]: Minggu ini saya belajar tentang kognisi...

[Author B]: Saya setuju dengan Author A, selain itu...
```

becomes a flat blob:

```
[Author A]: Minggu ini saya belajar tentang kognisi... [Author B]: Saya setuju...
```

The model loses all signal that this is a multi-author discussion with distinct
contributions. The `WHITESPACE_HANDLER` was designed for single-paragraph BBC news
articles (where it normalizes `\xa0` and similar whitespace artifacts); applying it to
structured forum text is a category error.

### Literature Basis

Bhatia et al. (2014) and Tarnpradab et al. (2018) both demonstrate that forum
summarization quality depends critically on preserving thread structure. Tarnpradab et
al. show that models using both sentence-level and thread-level representations
outperform structure-agnostic models, because the positional and authorial structure of
posts carries meaning about whose contribution is being summarized.

The most recent work in this area, ThreadSumm (Bhatt et al., 2026), finds that
*"standard LLM summarizers struggle to capture interleaved replies, quotes, and
overlapping topics"* specifically when thread structure is flattened before processing.

### Proposed Fix

Replace the blanket newline-collapse with a period-based separator that preserves
sentence boundary information across post boundaries:

```python
# Before (collapses all structure):
WHITESPACE_HANDLER = lambda k: re.sub(r'\s+', ' ', re.sub(r'\n+', ' ', k.strip()))

# After (preserves post boundaries as sentence separators):
WHITESPACE_HANDLER = lambda k: re.sub(r' +', ' ', re.sub(r'\n+', '. ', k.strip()))
```

This keeps `[Author A]: content. [Author B]: content.` as distinct sentences rather
than a run-on blob, giving the model better signal about authorial boundaries.

### References

- Tarnpradab et al. (2018). *Toward Extractive Summarization of Online Forum
  Discussions via Hierarchical Attention Networks.*
  https://arxiv.org/abs/1805.10390
- Tarnpradab & Jafariakinabad (2021). *Improving Online Forums Summarization via
  Hierarchical Unified Deep Neural Network.*
  https://arxiv.org/abs/2103.13587
- Bhatt et al. (2026). *ThreadSumm: Summarization of Nested Discourse Threads Using

## Supporting Analysis: BERTScore Floor Effect

The 0.63 vs. 0.73 BERTScore gap appears smaller than the real quality difference. This
is a known property of BERTScore in same-language evaluation.

BERTScore computes token-level cosine similarity using contextual embeddings from
a pretrained BERT model (Zhang et al., 2019). Because both the generated summary and
the reference are in Indonesian, they share a large portion of the embedding space
regardless of content — domain vocabulary (desain, interaksi, pengguna, usability)
inflates scores even for hallucinated outputs. The practical score range for
Indonesian-Indonesian summarization with multilingual BERT is approximately 0.60–0.90,
not 0.0–1.0.

The BERTScore authors acknowledge this and propose baseline rescaling: computing scores
relative to a baseline of randomly drawn sentences to correct for the inflated lower
bound. Rescaling was not applied in these evaluation runs; without it, the 0.63 baseline
is more accurately interpreted as "near-random content in the correct language" rather
than "partially correct."

The ROUGE scores do not suffer from this floor effect and are the more informative signal
here: mT5 ROUGE-1 = 0.11, Claude ROUGE-1 = 0.33 — a 3× gap that better reflects the
actual quality difference.

Bhandari et al. (2021) further note that BERTScore does not align closely with human
evaluation for summarization and recommend complementing it with ROUGE and human
judgment — which is consistent with this study's use of two annotators (Bryan and
Fathir) as reference summary sources.

**References:**
- Zhang et al. (2019). *BERTScore: Evaluating Text Generation with BERT.*
  ICLR 2020. https://arxiv.org/abs/1904.09675
- Bhandari et al. (2021). *Re-evaluating Evaluation in Text Summarization.*
  EMNLP. https://aclanthology.org/2021.emnlp-main.737/
- Freitag et al. (2021). *A Fine-Grained Analysis of BERTScore.*
  WMT. https://aclanthology.org/2021.wmt-1.59.pdf

## Issue 6: Missing Input Normalization Across All Backends

### Description

Prior to the cleansing patch, raw user-generated content entered the summarization
pipeline without sanitization. This introduced four categories of noise:

**1. HTML tags.** Forum posts written in a rich-text editor (Quill, TinyMCE, etc.) are
stored with HTML markup (`<p>`, `<br>`, `<b>`, `<ul><li>`). These tags tokenize as
arbitrary subword fragments that consume token budget and inject noise into model input
with no semantic contribution.

**2. Bare URLs.** Hyperlinks posted in discussions (`https://...`) can span dozens of
tokens and carry no content relevant to a summary. They inflate token counts, displace
meaningful text within fixed-size windows, and cause extractive models like LexRank to
select URL-heavy sentences as "representative."

**3. Unicode noise.** Web-originated text routinely contains non-breaking spaces
(` `), typographic quotes (`‘`, `’`, `“`, `”`), and other
Unicode compatibility characters. These tokenize differently from their ASCII
counterparts, introducing vocabulary fragmentation and tokenizer inconsistencies.

**4. Backend-inconsistent whitespace normalization.** `WHITESPACE_HANDLER` (the newline
normalizer) was applied only inside the mT5 code path. Claude, Gemini, T5-Indonesian,
and LexRank received raw text, so the same forum post could produce different token
sequences depending on the active backend — an undocumented inconsistency that
complicates cross-backend evaluation comparisons.

### Code (Before / After)

Before the patch, content was used with only a bare `.strip()`:

```python
content = post.get("content", "").strip()   # no sanitization
```

After the patch, a `clean_text()` step is applied at both input boundaries:

```python
def clean_text(text):
    text = _html.unescape(text)                    # &amp; → &, &lt; → <, etc.
    text = re.sub(r'<[^>]+>', ' ', text)           # strip HTML tags
    text = re.sub(r'https?://\S+', '', text)       # remove bare URLs
    text = unicodedata.normalize('NFKC', text)     # NBSP, curly quotes, ligatures
    text = re.sub(r'\n+', '. ', text.strip())      # newlines → sentence separator
    text = re.sub(r' +', ' ', text)                # collapse repeated spaces
    return text.strip()

# Applied at the two entry points:
content = clean_text(post.get("content", ""))      # summarize_post_thread
text    = clean_text(data["text"])                 # /summarize route
```

HTML entities are unescaped before tag stripping so that HTML-encoded markup
(`&lt;br&gt;`) is handled in the same pass as literal `<br>` tags.

### Literature Basis

Haddi et al. (2013) demonstrate that removing HTML markup and special characters from
web-originated text produces statistically significant improvements across text
classification and sentiment analysis tasks. They identify HTML tags as the primary
source of extraneous tokens in forum and review datasets, and show that failing to
strip them inflates feature-space noise while adding no discriminative signal — a
finding that applies directly to model input for summarization.

Manning, Raghavan & Schütze (2008) treat Unicode normalization and tokenization
normalization as foundational preprocessing steps in information retrieval. They note
that character-level inconsistencies — such as the distinction between the ASCII
apostrophe and the Unicode right single quotation mark — cause vocabulary fragmentation
and should be resolved before any downstream model sees the text.

The Unicode Consortium's Unicode Standard Annex #15 specifies NFKC (Normalization Form
Compatibility Decomposition followed by Canonical Composition) as the recommended
normalization form for natural language processing. NFKC maps compatibility characters
(curly quotes, ligatures, non-breaking spaces, full-width digits) to their canonical
equivalents, reducing vocabulary size and tokenizer fragmentation (Unicode Consortium,
2023).

Belinkov & Bisk (2018) show empirically that character-level noise — including Unicode
artifacts and encoding inconsistencies — significantly degrades neural
sequence-to-sequence model performance even when the errors are imperceptible to human
readers. Their analysis demonstrates that models trained on clean text are not robust
to tokenization-level noise at inference time, motivating proactive normalization
rather than reliance on model robustness.

## Summary of Issues and Fixes

| Issue | Root Cause | Fix | Status |
|---|---|---|---|
| 1 — Domain mismatch | mT5 trained on news (XL-Sum), not forum data | Use domain-appropriate model | Accepted as model limitation |
| 2 — Fragmentation | 512-token window splits forum into isolated chunks | Flat-then-truncate for mT5; keep hierarchical for LLMs | Proposed |
| 3 — Forced hallucination | `min_length=80` on short posts forces fabrication | Dynamic `min_length` proportional to input length | **Implemented** |
| 4 — Compounding errors | Bottom-up tree propagates leaf hallucinations upward | Eliminated by flat approach (Issue 2 fix) | Resolved by Issue 2 fix |
| 5 — Structure erasure | `WHITESPACE_HANDLER` collapses post separators | Replace `\n+` → `'. '` instead of `' '` | **Implemented** |
| 6 — Missing input normalization | Raw HTML, URLs, Unicode noise, and inconsistent whitespace across backends | `clean_text()` applied at both input boundaries | **Implemented** |
